## 0. 通用约定

- 一律**在用户已登录的真实 Chrome 里操作**（连 CDP，不新开无痕、不保存密码）
- `[已核验 2026-10-12]` **BOSS 掉登录不会去登录页**：搜索页直接跳回 `zhipin.com/`，页头出现「登录/注册」。网址里没有 `/login`，通用的 `classify_risk` 认不出，所以 `boss._guard` 另外用「登录/注册」判定为需要登录（停下提示、不上锁、不降速）。以前这会落成「页面异常」，连续 3 次被当成风控锁 1 小时 + 降速 24 小时
- 每开一个页面前必须调用 `ctx.budget.reserve(platform, stage)`
- 遇到验证码 / 限流 / 封禁页面：**立即停止该平台并写冷却锁**，不要重试
- 页面等待用 locator 自动等待，禁止 `sleep(4)` 这类固定等待

## 0.1 城市：受限平台 vs 自由文本平台 `[2026-10-10 补]`

同一个"城市"配置，四个平台的语义完全不一样：

| 平台 | 搜索参数 | 城市怎么给 | 受限吗 |
|---|---|---|---|
| BOSS直聘 | `city=101020100` | **9 位城市码**，由城市名查表 | ✅ 受限（373 个） |
| 前程无忧 51job | `jobArea=020000` | **6 位地区码**，由城市名查表 | ✅ 受限（**目前只有 15 个，是已知短板**） |
| 猎聘 | 城市名直接进 URL | 任意城市名 | ❌ 自由文本 |
| 智联招聘 | 城市名直接进 URL | 任意城市名 | ❌ 自由文本 |

**以前的坑**：BOSS 表里只有 20 个城市、51job 只有 15 个，用户填别的城市会被**静默跳过**——
任务显示"完成"，但一条岗位都没采到，看日志才发现。现在：

- `boss_cities.py` 里是 **373 个城市**，来自 BOSS 自己的公开接口
  `https://www.zhipin.com/wapi/zpCommon/data/cityGroup.json`；
  刷新用 `python tools\refresh_boss_cities.py`（<100 个城市就直接报错不覆盖，防接口变更）。
- 驱动暴露 `supported_cities` / `hot_cities`，`GET /api/cities?platform=` 把它交给界面。
- 配置页的城市是 **chip 输入**：有联想、能删、常用城市一键加；
  **表外的城市当场标红并写明"会被跳过"**，不用等跑完才发现。
- `city_code()` 现在也接受直接粘贴的城市码（从浏览器地址栏复制过来的那种）。

> 属于"参考 BossHunter 但用更干净的方式"：它的城市数据是随仓库分发的 JSON，
> 这里改成抓官方接口 + 一个可复现的刷新脚本，来源和抓取时间都写在文件头。

### 1.4.1 城市：只能用它自己的 6 位地区码 `[2026-10-10 实测]`

51job 的 `jobArea` **只认 6 位地区码**，中文城市名会被**直接忽略**：

| 请求 | 实际结果 |
|---|---|
| `jobArea=上海` | 返回全国混合结果（贵阳 / 上海 / 深圳 都在里面） |
| `jobArea=杭州` | 返回**同一批**全国混合结果 |
| `jobArea=020000` | 正确按上海过滤（驱动现在用的就是这个） |

那完整的城市码表能不能取到？两条路都试过，结论是**取不到**：

1. **公开静态资源里没有**：把搜索页引用的 17 个 JS（含 `we-vue-bundle.js` 与全部
   `app-*.js`）全下来搜 `020000` → 0 命中；搜城市名 → 也没有。
2. **城市选择器只暴露名字**：弹窗（"选择城市 1/5"）里能看到热门城市与 A-Z 全量列表，
   但这些节点的 `href` / `data-*` 里**都不带码**；码是点选之后由前端算出来再拼进 URL 的。
   想靠"点一个城市读一次 URL"凑齐 ~300 个码，成本远大于收益。

所以 51job 目前**只支持内置的 15 个城市码**（上海/北京/广州/深圳/杭州/成都/南京/武汉/西安/
苏州/重庆/天津/长沙/郑州/青岛）。界面上：

- 这 15 个会作为「常用」一键添加；
- 填了表外的城市会**当场标红**并写明"会被跳过"；
- 采集时如果一个可用城市都没有，任务会明确停手并说明原因（不会静默"完成"）。

> 这是**已知边界**，不是待办：要扩容只能拿到 51job 的地区码接口（需要签名），
> 或者人工逐个核验 —— 两条路都不划算。真要在其它城市用 51job，可以在平台上自己搜。

### 1.5 备选：只读搜索 API（用于纯采集，更稳）
`[已核验]` 页面上下文内 `fetch` 调 `we.51job.com/api/job/search-pc`：单次返回列表 + JD
（`jobDescribe`），每页 20 条、`totalCount` 可反推真实末页（结果封顶 50 页）。
**风控铁律**：HTTP 非 200 / 非 JSON / 登录或验证码信号 → 立即停止，**不重试**。

## 4. 新增一个平台怎么做

1. 建 `platforms/<key>.py`，实现 `PlatformDriver`：`key / name / capabilities / collect / apply / monitor`
2. 用真实登录的 Chrome 逐项确认**选择器清单**（写进本文件，标注日期）
3. 在 `platforms/registry.py` 注册
4. `capabilities` 只声明**已实机验证过**的动作；没验证的不要声明
5. 跑 `tests/test_registry.py` + 该平台的实机验收清单（见 07）

### 5.4.1 投递预演 `[2026-10-10 实机]`

自动投递迟迟没开放，卡的不是"选择器不知道"，而是"点了会真的把消息发出去"。
所以先把**只需要看、不需要发**的那部分验掉 —— `POST /api/jobs/{id}/probe-apply`
（走和采集详情页**完全相同**的页面预算与风控闸门，打开页面看一眼就关掉）：

| 检查项 | 实机结果（两个真实岗位各一次） |
|---|---|
| 沟通按钮 | ✅ 存在且可见：`selector=.btn-startchat`，文本「立即沟通」 |
| 登录态 | ✅ 不在登录墙后面（`need_login=false`） |
| 风控信号 | ✅ 没有（URL/正文都没命中 captcha / rate_limit / blocked） |
| 是否发送了东西 | ✅ `sent_anything=false` —— 一个点击都没有 |

> 踩坑记录：第一版把 `needLogin` 写成"DOM 里有没有 `.login-dialog`"，
> 结果永远为真 —— BOSS 每个页面都埋着**隐藏的**登录弹窗。改成"可见才算"之后才正确。

**结论**：页面结构完全支持自动投递，已实机跑通 —— 细节见下面 5.4.2。

### 5.4.2 自动投递 `[2026-10-10 实机核验 · 已开放]`

**真实机制（最重要的一条事实，推翻了原先的猜测）**：按下「立即沟通」的那一瞬间，
**BOSS 会用账号里已有的默认招呼语直接把消息发出去** —— 不需要程序再点发送。
也就是「点一下」和「发第一条消息」是同一个动作，不存在「先点开、再决定发不发」的中间态。

实机跑通的完整流程：

| # | 动作 | 选择器 / 结果 |
|---|---|---|
| 1 | 打开岗位详情页（占一次投递页面额度） | `https://www.zhipin.com/job_detail/{id}.html` |
| 2 | 点「立即沟通」 | `.btn-startchat` → **平台立刻发出默认招呼语**（对方是真实 HR） |
| 3 | 页面不跳转，右下角弹出聊天面板 | `.dialog-wrap.startchat-dialog` |
| 4 | 填入 AI 生成的个性化招呼语 | `textarea.input-area`（placeholder 是「请简短描述您的问题」） |
| 5 | 点发送 | `div.send-message`（**只在输入框有文字之后才出现**） |
| 6 | 核验送达 | 面板里出现「已发送」→ 记为 `applied` |

**幂等保护（绝不重复打扰同一个 HR）**：按钮文本已经是「继续沟通」时，说明这个岗位早就聊过，
`apply()` 直接返回 `already`，**一个点击都不做**。

**代码位置**：`src/jobpilot/platforms/boss.py` 的 `BossDriver.apply()`；`capabilities` 现在是 `collect + apply`。

**发消息也要过风控闸门**：写个性化招呼语那一步走 `Policy.authorize(Action(kind=SEND_MESSAGE))`，
和投递共用时间窗、随机休息日、采集→投递冷却等规则；被拒时**不点发送**。

**已生效的风控**（不需要新增代码）：
每日页面预算（BOSS 40/200/30/30）、滚动速率窗口（8 次/10 分钟、30 次/小时）、开页面节流（2.5–7 秒 ×2.0）、
活跃时段（08:00–22:00）、采集→投递冷却（5–15 分钟）、每日投递上限 30、命中风控后 60 分钟冷却 + 24 小时降速 ×2。

**开关**：`config.yaml` → `platforms.boss.apply`（默认关闭）。打开前想先确认页面结构没变，可以跑「投递预演」——它只打开岗位页看一眼，不点、不发。

**真机首跑记录（2026-10-10 22:45）**：任务 `83282ac9`（mode=apply, platform=boss），结果是 `already: 1 / applied: 0 / failed: 0`，
岗位状态落成 `already`，今日投递额度一分没动。
之所以挑这个岗位，是因为它当天已经打过招呼 —— 走的是「继续沟通 → already」这条分支，
全程一个点击都没发生。真正的「第一次打招呼」分支，同一天早些时候已经用同一台机器手工点通过（见上面的机制说明）。

### 5.4.3 自动监测：只读列表，不进会话 `[2026-10-11 实机核验选择器]`

监测的**唯一副作用**是「点进会话会把未读标成已读，而且撤不回来」（HR 那边会看到已读不回）。
所以这一版监测**只读聊天列表页**，一个会话都不点开 —— 拿得到「谁回了我 / 最后一句说了什么 /
HR 读没读我的消息」，拿不到完整对话。这个取舍是故意的。

列表页结构（2026-10-11 在真实登录环境抓的 40 条会话）：

| 元素 | 选择器 | 实机结果 |
|---|---|---|
| 会话行 | `li[role=listitem]` | ✅ 40 条 |
| 姓名 / 公司 / HR 职位 | `.name-box span` 的 [0] / [1] / [2] | ✅ |
| 最后一条消息 | `.last-msg-text` | ✅ |
| 状态徽标 | `.message-status` | ✅ 只有 [已读] / [送达] 两种，**且只出现在我自己发的最后一条消息上** |
| 时间 | `.time` | ✅ 昨天 / 10月09日 |

**判定规则**（`classify_chat_row()`，全部来自那 40 条真实样本）：

| 会话行长什么样 | 结论 |
|---|---|
| 带 [已读] 徽标 | 我发的最后一条、对方看过了 → `viewed` |
| 带 [送达] 徽标 | 我发的最后一条、对方还没看 → 不算进展，跳过 |
| 不带徽标 + 系统提示（您的附件简历…已发送） | 机器发的 → 跳过 |
| 不带徽标 + 我自己发的附件（只剩文件名，如 张三-简历.pdf） | 跳过 |
| 不带徽标 + 回绝模板（并不完全一致 / 祝您） | `rejected` |
| 不带徽标 + 提到面试 | `interview` |
| 不带徽标 + 其它 | `replied`（对方说话了） |

**状态只往前走**：`viewed(1) → replied(2) → rejected(3) → interview(4) → interviewed(5) → offer(6)`，
低的不覆盖高的 —— 否则 HR 回过话之后我又发了消息（徽标变回 [已读]）会把线索「退回已查看」。

会话列表里没有岗位标题，只能靠公司名把会话对回岗位池；同名公司有多个岗位时**不匹配**（不猜）。
对上了才写 `job_id`，监测页就能显示岗位标题和公司。

**现状**：代码在 `src/jobpilot/platforms/boss.py` 的 `BossDriver.monitor()`，单测在 `tests/test_monitor.py`，
并且在真实浏览器上验证过「能打开列表页、在登录墙前 fail-closed」。
但**还没有在真机上跑通一次完整任务** —— 所以 `capabilities` 里暂时没有 `monitor`，界面仍显示「未开放」。

> **踩坑记录（2026-10-11）**：核验当天那个 Chrome 连不上 `connect_over_cdp`
> （`Network.setCacheDisabled ... type: closed`），**整个 JobPilot 都开不了页面**，不只是监测。
> 查出来是 25 个残留的 patchright 驱动进程（`patchright\driver\node.exe`）占着 CDP 会话；
> 清掉之后仍复现，于是用**全新临时 Chrome 实例**对照验证，驱动本身是好的（连得上、能开页），
> 说明问题出在那个 Chrome 实例的长期状态 —— 重启 Chrome 即可。
> 顺带修了两个被这件事暴露出来的毛病：启动脚本的就绪探测原来打 `/api/health`（要连浏览器，
> 于是「服务明明起来了」被判成「启动失败」），改成 `/api/status`；
> `PatchrightBrowser.health()` 原来真的去 `connect_over_cdp`，浏览器异常时会卡几十秒到几分钟，
> 改成打 `/json/version`（2 秒超时）。

### 5.5 结论
- **采集**：已实现（`platforms/boss.py`）
- **投递（打招呼）**：**已实机核验并开放**（见 5.4.2）
- **监测**：**只读聊天列表**版本已实现（见 5.4.3），选择器与判定规则均来自 40 条真实会话；
  因为还没在真机上跑通完整任务，`capabilities` 里暂时不声明 `monitor`。
  「点进会话读全文」那一版有副作用（会把未读标成已读、HR 看到已读不回），另需你单独确认。

### 6.0.1 JD 正文抓取（2026-10-10 实测）

| 平台 | JD 容器 | 详情 URL | 实测 |
|---|---|---|---|
| 51job | `.bmsg` | `jobs.51job.com/all/{jobId}.html` | 494 / 403 / 634 字 |
| 猎聘 | `.job-intro-container` | `www.liepin.com/job/{id}.shtml` | 641 / 857 / 1243 字 |
| 智联 | `.describtion-card__content-wrap` | `www.zhaopin.com/jobdetail/{number}.htm` | 755 / 303 字 |

**踩过的两个坑**（都已在代码里处理）：

1. **容器先出现、正文后渲染**：`wait_for` 拿到容器 **不代表里面有字**。第一次实现就吃了这个亏——
   开页额度花了、JD 却是空的，而且**没有任何报错**。现在改成"轮询直到拿到非空文本"。
2. **抓 JD = 开一次详情页 = 吃掉一次 `collect_detail` 额度**：所以做成可选开关
   （`platforms.<平台>.fetch_detail`，**默认关**）。预算用尽时**不失败**：
   停止抓 JD 并打一行日志，列表字段照常入库。

### 6.1 前程无忧 51job ✅ 最好接

### 6.4 三个平台的共性结论
1. **只依赖语义类名 / data-nick / href 结构**，绝不用哈希类名或不稳定的样式类
2. **列表能拿到的字段就先拿到**，能不开详情页就不开（风控 + 速度双赢）
3. 每个平台都要**先跑一遍 [07](07-开发与验收.md) 的实机验收清单**才算数
