# 06 · 风控与安全

自动投递是账号风险最高的动作。本项目把"防封号"做成**硬约束**，而不是靠开发自觉。

## 1. 三条硬约束

### 1.1 页面预算（账号级）
每次**打开一个页面**之前，先向 `safety.budget` 申请额度：

```
budget.reserve(platform="51job", stage="collect_search")
```

- 按「平台 + 阶段 + 本地日期」计数，超限直接抛 `BudgetExceeded`，当天该平台停止
- 阶段：`collect_search`（搜索页）/ `collect_detail`（详情页）/ `apply`（投递页）/ `monitor`（监测页）
- 另有 `total` 总量上限兜底
- 为什么必须统一计数：采集、投递、监测都会开页面，**账号风控看的是总量**，任何一环漏算都白搭

默认值（`config.safety.daily_pages`）：

| 阶段 | 默认上限 |
|---|---|
| 采集-搜索页 | 60 |
| 采集-详情页 | 300 |
| 投递 | 60 |
| 监测 | 40 |
| 总量 | 500 |

### 1.2 冷却锁（按平台）
- 触发验证码 / 限流 / 封禁 → 写 `locks[platform]`，冷却期内该平台**不投递、不采集、不监测**
- **按平台隔离**：51job 被锁不影响猎聘、智联
- 默认冷却 30 分钟（`config.safety.risk_lock_minutes`）

### 1.3 节流
| 项 | 说明 | 默认 |
|---|---|---|
| **开页面节流** | **两次开页面之间强制间隔：截断正态（有中心节奏，不是均匀随机）× 平台倍率，每平台独立计时** | 2.5–7 秒 × 1.5 |
| **突发聚集惩罚** | **短时间内连着开页面额外多等**（15 秒内 ≥3 次 +1.2~2.8 秒；45 秒内 ≥6 次 +4~7 秒） | 自动 |
| **活跃时段** | **不在 `active_windows` 内时，开页面直接拒绝**（半夜刷招聘同样是机器特征） | 06:00–24:00 |
| **速率窗口** | **滚动窗口内的页面上限：超速先等到窗口滑过去，等太久就停手** | 10 分钟 15 页 / 1 小时 60 页（BOSS 8 / 30） |
| **采集→投递冷却** | 采完不能马上投，冷却一段随机时间 | 5–15 分钟 |
| **页面失败熔断** | 连续读不到预期内容即锁该平台 | 3 次 |
| 发送时间窗 | 只在时间段内投递 | `08:00-22:00` |
| 投递间隔 | 两次投递之间在 `apply.interval_min`–`interval_max` 内取**截断正态** + ±25% 抖动 | 60–180 秒 |
| 随机休息日 | 按概率整天不投递 | 5% |
| 渐进退避 | 连续失败等待 60 → 120 → 300 秒 | 自动 |
| 每日投递上限 | 成功投递数达到即停 | 30 |
| 冷却时长随机化 | 风控冷却 30 分钟 × (1 ± 35%)，避免"精确 30 分钟"这种机器特征 | 0.35 |
| **命中后降速** | **冷却结束也别按原速继续：接下来 24 小时内开页面间隔额外 ×2** | 24h × 2 |
| **跨平台联动熔断** | **24 小时内 ≥N 个不同平台各自命中风控 → 整体冷却到当天结束（至少 4 小时）**：账号级信号，换平台继续跑是最糟的选择 | N=2（safety.cross_platform_risk_platforms，0=关闭） |

> **开页面节流是第一条也是最重要的一条**：机器人最明显的特征不是"投得多"，而是
> **零间隔连续开页面**。它被放在唯一闸门里，驱动绕不过去。

**为什么不用「均匀随机」**（2026-10-11 改）：均匀随机的期望「每分钟开页数」是一条平直的线，
而平直本身就是可以统计出来的特征 —— 平台只要看一段时间的间隔分布就能把脚本挑出来。
真人是有中心节奏的：多数时候接近某个值，偶尔快、偶尔停一下。所以间隔改成**截断正态**
（均值居中、±3σ 覆盖配置区间、超出就截回来），投递间隔同理。

**突发聚集惩罚**：现实里的「猛刷」往往不是剧本，而是重试、页面秒开、循环没控制好造成的**意外聚集**。
它恰恰是平台最容易抓的特征，于是在唯一闸门里主动把它吃掉 —— 短时间连着开页面就额外多等一会儿：
慢一点，但不像机器。

**速率窗口（为什么在日预算之上还要再叠一层）**：日预算只回答"今天最多开多少页"，
不回答"这 500 页是摊在一整天里开的，还是十分钟里刷完的"。
可以按 `config.safety.max_pages_per_10min` / `max_pages_per_hour` 限制滚动窗口用量：

- 超速时先**等待**窗口滑过去（等待走 `stop.sleep`，暂停/停止能立刻打断），任务只是变慢；
- 需要等的时间超过 `rate_wait_max_seconds`（默认 900 秒）就直接**停手**并说明原因——
  等 40 分钟才放行等于任务卡死，不如明天再来；
- 被速率挡下的那次**不消耗**页面预算（速率闸门排在预算之前）。

这条属于 BossHunter 没考虑到的部分：它有每日上限，但"短时间猛刷"照样会触发平台风控。

### 1.4 与 BossHunter 对照：我们顺手修掉的问题

BossHunter 的风控整体是好的，参考它的过程中发现两处问题，本项目不沿用：

| BossHunter 的做法 | 问题 | 本项目的做法 |
|---|---|---|
| `platform_safety_state` 只有一行（`CHECK id=1`） | 一个平台被锁，**所有平台连坐** | `locks` 表按平台一行，互不影响 |
| 日上限用 `DATE('now')`（UTC） | 北京时间早上 8 点才重置 | 一律 `date(...,'localtime')` |

同时补上了 BossHunter 有、而本项目之前缺的三条：**开页面节流**、**采集→投递冷却**、
**连续页面失败熔断**。

### 1.5 界面上能改的风控旋钮

**原则：界面上出现的旋钮必须真的被代码读到。** 一个点下去没有任何作用的开关，
比没有这个开关更糟——它会让人以为自己在控制风险。（本轮就把配置页里
`monitor.enabled` / `monitor.auto` 两个**假开关**删掉了：数据模型里有字段，
但没有任何一处代码读它，四个平台的 `capabilities` 也都不含 `monitor`。）

现在配置页的「风控」分组逐项对应：

| 界面字段 | 配置键 | 默认 | 作用 |
|---|---|---|---|
| 开页面最短/最长间隔 | `safety.page_interval_min/max_seconds` | 2.5 / 7 | 两次开页面之间随机等待（每平台独立计时） |
| 保守系数 | `safety.delay_multiplier` | 1.5 | 所有等待时间整体放大 |
| 命中风控后冷却 | `safety.risk_lock_minutes` | 30 | 冷却期内该平台不投递/不采集/不监测（±35% 随机化） |
| 命中风控后降速持续 | `safety.risk_penalty_hours` | 24 | 冷却结束后还继续放慢多久（0 = 关闭） |
| 降速倍数 | `safety.risk_penalty_factor` | 2.0 | 惩罚期内的额外倍率（1.0 = 关闭） |
| 连续失败熔断阈值 | `safety.max_consecutive_page_failures` | 3 | 连续读不到预期内容就锁平台 |
| 随机休息日概率 | `safety.day_off_probability` | 0.05 | 按概率整天不投递 |
| 允许发送的时段 | `safety.send_windows` | `08:00-22:00` | 窗口外任何发送动作直接拒绝 |
| 允许**开页面**的时段 | `safety.active_windows` | `06:00-24:00` | 窗口外连页面都不开（空列表 = 不限）；界面顶部会提示"不在活跃时段" |
| 每日页面预算 ×5 | `safety.daily_pages.*` | 60 / 300 / 60 / 40 / 500 | 每开一次页面记一次，用完当天停手 |
| 同一页不重复采 | `safety.recollect_after_hours` | 6 小时 | **按页记账**：重复点采集不会重开同一页；采集被打断时也只重做没做完的页（0 = 每次都采） |
| 近 10 分钟页面上限 | `safety.max_pages_per_10min` | 15（BOSS 8） | 滚动 10 分钟窗，防突发 |
| 每小时页面上限 | `safety.max_pages_per_hour` | 60（BOSS 30） | 滚动 1 小时窗，防持续高速 |
| 超速时最多自动等多久 | `safety.rate_wait_max_seconds` | 900 | 超过就停手，而不是无限等待 |

> **BOSS 更保守**：`safety.platforms.boss` 覆盖了更小的页面预算、更大的倍率（2.0）和更长的冷却（60 分钟），
> 因为它对自动化最敏感。覆盖率只写想覆盖的字段，其余继承全局默认。

### 1.6 「关页面」和「停止」不是一回事

| 动作 | 结果 |
|---|---|
| 关掉看板页面 | 只是关掉遥控器：**没有任务在跑时**，2 分钟后服务自动退出（`server.idle_shutdown_minutes`） |
| 关掉页面但任务在跑 | 服务**不退出**，任务继续在后台开页面、继续投递 |
| 点右上角「停止」 | 软停止：不再开始下一个动作，但会把当前这一个动作做完，避免投到一半 |

这条差异很关键：无人看管的后台投递正是最危险的状态，所以接口层做了三件事——
任务卡在运行时会明说"关页面不会停止它"、关页面时弹一次确认、停止按钮的悬停提示写清语义。
## 2. 风险信号识别

从**页面 URL** 和**正文文本**两个来源识别，命中即 fail-closed：

| 类型 | 证据（判断顺序：登录墙 > 封禁 > 验证码 > 限流，按严重程度而不是按匹配顺序） |
|---|---|
| `login_required` | URL 含 `login / signin / sign-in / passport / uplogin / web/user` → 停止但**不写冷却锁**（只是登录过期，重新登录即可） |
| `blocked` | 正文含「账号存在异常 / 账号被限制 / 账号被冻结 / 您的账号存在风险 / 访问被拒绝 / 访问受限 / 已被封禁」 |
| `captcha` | URL 含 `/verify /captcha geetest security-check /challenge`；正文含「请完成验证 / 完成安全验证 / 拖动滑块 / 人机验证 / 滑动验证 / 验证码 / 校验码」 |
| `rate_limit` | 正文含「操作 / 访问 / 请求过于频繁、访问速度过快、访问频率、系统繁忙、服务繁忙、当前访问异常、访问行为异常」 |

**泛化短语单独不算数**（`RISK_SOFT`）：像「请稍后再试」这种话普通岗位描述里也会出现（真踩过：
一句 JD 里的「如未接通请稍后再试」差点被当成限流把整个平台锁了），所以它必须和
「访问 / 请求 / 操作 / 系统 / 服务 / 网络 / 频繁 / 异常 / 繁忙 / 验证」里的词**同现**才判为限流。

**为什么词表要列这么多近义说法**：四个平台的说法不一样，而且它们会改文案。漏判的代价不是「少拦一次」，
而是把一次限流当成「页面改版」—— 于是（a）上锁理由写错、（b）风控事件被记成 `page_error`，复盘时看不到真因。

## 3. 人工确认

- 评分通过 → `pending_confirm`，**绝不自动投递**
- 用户确认 → `approved`；拒绝 → `rejected`
- `full` 全流程在确认门开启时**在评分后停下**，等用户确认后再点"投递"
- 关闭确认门（`confirm.required=false`）才允许评分通过即投

## 4. 明确的"不做"

- 不破解/绕过验证码
- 不绕过登录墙
- 不做浏览器指纹伪装、不换代理规避
- 不提高默认频率（这是项目边界）

## 5. 失败语义

投递失败必须落库并区分原因，不允许笼统记成"失败"：
`already`（已投过）/ `need_resume`（需完善简历）/ `need_login`（登录失效）/
`unsupported`（找不到按钮或被拦）/ `failed`（其它）

**重复投递比漏投更危险**：投递前先查该岗位是否已投（状态 + events 双重判断）。

**"按设计停手"不算失败**：预算用完、平台冷却、速率超速、时间窗之外、随机休息日……
这些都是闸门在正常工作，驱动遇到它们要记录原因并正常收尾（`is_graceful_stop()` 是唯一判定），
不能抛成一条吓人的任务失败记录——否则用户会以为程序坏了，实际是安全内核在保护账号。

## 6. 看板只给本机用

看板只监听 `127.0.0.1`，局域网里的其它机器连不上。但它挡不住**你自己浏览器里打开的别的网页**：

| 攻击 | 怎么做到的 | 不挡会怎样 | 怎么挡 |
|---|---|---|---|
| DNS 重绑定 | 恶意网页把自己的域名临时解析到 127.0.0.1，于是它和看板「同源」 | 能读简历（`/api/resume`）、下载备份（`/api/backup`，里面有 `config.yaml` 和真实 API Key） | 请求头 `Host` 必须是本机地址：重绑定之后 `Host` 仍是它的域名 |
| 跨站提交 | 任何网页都能往 `127.0.0.1:8700` 发 POST（拿不到响应，但动作会生效） | 停止任务、确认岗位、触发投递预演（会真的开页面） | 写操作的 `Origin` 必须是本机页面；浏览器发跨站请求一定会带 `Origin` |

实现在 `web/app.py` 的 `_local_only_problem()`，作为最外层中间件：被拒的请求到不了任何路由，返回 403 和原因。
命令行脚本（`tools/`、curl）不带 `Origin`，照常可用；用 `localhost` 打开看板也可以。
