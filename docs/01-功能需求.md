# 01 · 功能需求

## 1. 项目定位

JobPilot 是**单机、单用户**的多平台求职助手：在本机 Chrome 里用用户自己的登录态，完成
「采集岗位 → AI 评分 → 生成招呼语 → 人工确认 → 自动投递 → HR 监测」的闭环。

不做的事（明确划出边界）：
- 不破解验证码、不绕过登录墙、不做指纹伪装
- 不做多账号、不做云端托管、不做批量营销
- 不保证自动投递一定成功（平台反爬会导致失败，这是现实）

## 2. 平台能力矩阵

| 平台 | collect | apply | monitor |
|---|---|---|---|
| BOSS直聘 | ✅ | ✅ 已核验 | ❌ 未核验 |
| 前程无忧 51job | ✅ | ❌ 未核验 | ❌ 未核验 |
| 猎聘 | ✅ | ❌ 未核验 | ❌ 未核验 |
| 智联招聘 | ✅ | ❌ 未核验 | ❌ 未核验 |

> 这张表是**实机核验的结果**，不是期望：`capabilities` 里只写真的跑通过的动作，
> 界面「风控仪表」里每个平台名旁边的能力标签就是照它渲染的。投递/监测在选择器和结果核验都实机通过之前一律不声明，
> 因为"界面上有按钮但一点就失败"比"没有按钮"更糟。

> **BOSS 投递的实机事实（2026-10-10）**：点「立即沟通」的一瞬间，平台就会用账号里的**默认招呼语**
> 直接把消息发给对方 HR（这一步本身就是投递）；随后右下角弹出聊天面板，可以再补一条 AI 生成的
> 个性化招呼语。按钮文本变成「继续沟通」时说明早就聊过，系统直接判为 already，绝不重复发。
>
> **BOSS 监测的现状（2026-10-11）**：只读聊天列表的版本已经实现（选择器与判定规则来自 40 条真实会话），但还没在真机上跑通一次完整任务，所以 `monitor` 暂时不声明 —— 界面上的「未开放」是准确的。

能力集驱动：`PlatformDriver.capabilities`，服务层与前端都按它裁决，不写 if platform == "xxx"。

## 3. 功能清单

### 3.1 采集
- 输入：每平台的关键词列表 + 城市列表 + 每关键词最大页数
- 输出：岗位入库（跨平台按「公司+标题」归一化去重）
- 约束：串行（同一时刻只跑一个平台）；每翻一页前先过页面预算
- 关键词来源：手填，或用 `POST /api/suggest-keywords` 让模型**看着简历和已采结果**推荐
  （提示词里会带上当前用词、每个词的实际平均分、已采岗位样本 —— 所以建议是有依据的，不是泛泛而谈）
- 断点 / 去重：**同一个「城市+关键词」的同一页**在 `safety.recollect_after_hours`（默认 6 小时）内不重复采（按页记账，
  直接跳过并计入 `skipped`。为什么算风控：重复点一次"采集"会把同样的搜索页再开一遍，
  一个新岗位都多不出来，却实打实多花一次页面预算。想强制重采就把这个值设为 0。
- 岗位级去重（job id）+ 跨平台去重（公司+标题归一化）另有一层，词级去重只是省页面

### 3.2 评分
- 两段：**硬规则预筛**（实习/黑名单/薪资区间）→ **AI 评分**（0-100）
- **简历读不到就直接拒绝评分**（fail loud）：以前会退化成拿「（未提供简历）」去让模型打分，
  产出一批看起来正常、实际毫无意义的分数，还会一路推着岗位走向投递。
  简历的统一读取入口是 `ServiceContext.resume_text()`（相对路径按项目根解析，四个服务共用）。
- 预筛命中直接 rejected，不消耗 AI 额度
- 预筛内容：实习（可配）· 黑名单词 · 薪资区间 · **岗位性质**
  （`jobpilot.nature`：外包/派遣、培训招生、营销话术三类规则，
  默认只标记不剔除，填进 `profile.block_natures` 才直接拒）
- 支持并发调用 AI（1-3），数据库写入始终串行
- 失败可重试；整批失败时明确报错，不静默

### 3.3 招呼语
- 为「待确认/已通过」岗位生成 40-90 字招呼语，落库可编辑可复制
- AI 不可用时该步骤整体跳过（不阻塞流程）

### 3.4 人工确认（默认开启）
- 评分通过 → `pending_confirm`，**不会自动投递**
- 用户在界面逐个/批量确认 → `approved`；或全部拒绝 → `rejected`
- 关闭确认门（配置）后，评分通过直接进入 `approved`

### 3.5 投递
- 只对 `approved` 岗位执行，一岗一次，绝不重复投
- 顺序闸门：平台能力 → 冷却锁 → 时间窗 → 随机休息 → 每日上限 → 逐岗投递
- 失败分级落库：`failed / need_resume / unsupported / already`
- 送达/结果核验：识别"投递成功/已投递/需完善简历"并据此落库
- **手动投递回执**：自动投递未核验之前，真实投递是人在平台上手点的。
  `POST /api/jobs/{id}/applied` 把"我确实投了"记进系统：状态 → `applied`、
  写 `apply` + `applied` 事件，**与自动投递同一套计数**——所以手动的次数同样占今日额度、
  同样进跟进队列。否则今日额度、跟进提醒、统计会一起跟真实情况对不上。
  另外提供"打开并复制招呼语"：一次点击 = 打开发送页面 + 招呼语进剪贴板，回来粘贴就能发。

### 3.6 监测
- 按平台抓取"已投递"状态与 HR 互动，识别：邀面试 / 拒绝 / 已查看 / 已回复 / 感兴趣
- 事件去重：同一状态不重复写时间线
- 监测也受页面预算与冷却锁约束

### 3.7 进展追踪（投递之后）

- 手动记录每个岗位的进展：已查看 / 已回复 / 约面试 / 面试完 / 拿到 offer / 被拒
- 存在 `interactions`（同一岗位一条，改状态是**更新**而不是追加），并写一条 `progress` 事件进时间线
- 求职漏斗因此能画到"面试 → offer"，而不是停在"已投递"
- 为什么先做人工记录：HR 监测驱动还没核验，而"谁约了我面试"这件事每天都要用；
  等监测驱动可用时，它写进同一张表、同一套状态，界面不用改

### 3.7.1 面试准备

- 输入：简历 + 岗位（标题/公司/城市/薪资）+ 该岗位 JD + 已记录的进展
- 输出：6-8 个针对这份 JD 的问题，每个带「他想确认什么」和「你可以讲简历里的哪段经历」，
  外加最多 3 条可能被追问的短板
- **硬要求**：`angle` 只能引用简历里已有的经历；简历里没有就写「如实说明」，不许编
- 简历读不到、或岗位没有 JD → **直接拒绝**（没有 JD 只会产出通用题清单，那不如不做）

### 3.8 配置 / 任务 / 导出
- 配置：YAML，界面可改，pydantic 校验
- 任务：后台任务（采集/评分/招呼语/确认/投递/监测/全流程），可暂停、可停止、有进度
- 导出：岗位表导出 CSV/XLSX（可选）

## 4. 岗位状态机

```
new ──评分通过──▶ pending_confirm ──确认──▶ approved ──投递──▶ applied
 │                     │                                        │
 │                     └──拒绝──▶ rejected                      ├─▶ already
 ├──预筛命中──▶ rejected                                        ├─▶ need_resume
 └──评分未通过──▶ filtered                                      └─▶ failed
                                    applied ──HR回复──▶ replied ──▶ interview / rejected
```

## 5. 非功能需求

| 项 | 要求 |
|---|---|
| 启动 | 一条命令起服务；无多余控制台窗口 |
| 性能 | 采集 1 页 < 5s；评分并发 3 时吞吐 ≥ 顺序的 2 倍；DB 写入不阻塞 API |
| 可靠性 | 任意一步失败不丢数据；任务可停止且已完成结果保留 |
| 可测性 | 非浏览器逻辑单元测试覆盖率 ≥ 80%，不需要 Chrome |
| 可维护 | 新增一个平台 = 新增一个驱动文件 + 一份选择器清单，不改服务层 |
