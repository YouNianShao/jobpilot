# 03 · 数据模型

> 表结构来自 `db.py` 的 `_MIGRATIONS`（`schema_version` 当前 = 9）。
> 改表必须加迁移，不能改历史迁移。

## 1. 存储

- 引擎：SQLite，`data/jobpilot.db`
- 模式：`PRAGMA journal_mode=WAL`（读写不互锁）、`foreign_keys=ON`
- 迁移：`schema_version` 表 + 顺序脚本，只前进不回滚；需要 Python 回填数据的版本在 `_MIGRATION_HOOKS` 里（如 v9 回填 `norm_*`）

## 2. 表

### jobs（岗位）

```sql
id / platform / external_id / title / company / salary / city / url / jd
score / score_reason / greeting / status / dup_of
resume_path / follow_up / follow_up_at / deleted_at
created_at / updated_at
norm_title / norm_company        -- v9：normalize(title / company)，只给跨平台去重的索引用
```

- `id` = `平台-平台岗位号`（如 `boss-5df0a359…`）
- `deleted_at` 非空 = 在回收站里（所有列表默认过滤掉）
- `resume_path` 指向该岗位的定制简历文件；`follow_up` / `follow_up_at` 是跟进话术与生成时间
- 索引：`status`、`platform`、`deleted_at`（回收站过滤用），以及 v9 加的：
  - `(norm_title, norm_company)`：跨平台去重一次索引查找（以前每入库一条就全表读出来在 Python 里比，2 万岗位时每条 113ms）
  - `(deleted_at, created_at)` / `(deleted_at, status, created_at)` / `(deleted_at, score, created_at)`：岗位池分页
    「过滤列在前、排序列在后」，按索引顺序直接取一页，不用先把全部岗位取出来排序；第二条同时覆盖状态分档计数
  - `(deleted_at, id, updated_at)`：岗位性质缓存只读这两列，不回表
- `norm_*` 是派生列：`Job` 上同名的是按 `title` / `company` 现算的属性，读库时会被过滤掉
- 全表聚合（漏斗 / 公司分布）写成 `WHERE +deleted_at IS NULL`：一元加号让 SQLite 不用索引、直接扫表。
  几乎所有岗位都满足这个条件，走索引再逐条回表反而慢一倍多

### events（时间线，替代老的 history）

```sql
id / job_id / kind / detail / created_at
```

- `job_id` 为空 = **全局事件**（风控命中、速率停手、页面异常、采集/监测汇总）
- `kind` 常见值：`collected` · `prefilter_rejected` · `scored` · `greeting` · `confirmed` ·
  `confirm_rejected` · `apply` · `applied` · `progress` · `interview_prep` · `resume` ·
  `follow_up` · `probe_apply` · `collect` · `monitor` · `risk` · `page_error` ·
  `risk_lock` · `rate_stop`
- 索引：`job_id`、`(kind, created_at)`、`(kind, job_id, detail)`（v9，关键词效果按岗位取第一条采集事件）

### interactions（HR 互动 / 进展）—— 注意：它同时承载"手动进展"

```sql
key / platform / job_id / hr_name / state / last_text / deeplink / seen_at
```

- 手动记录的 `key` = `manual:{job_id}` → **同一岗位改状态是 UPDATE 不是追加**
- 将来 HR 监测驱动写进来的记录用 `平台:会话号` 作 key，同一张表、同一套 state
- `state` 取值：`viewed` · `replied` · `interview` · `interviewed` · `offer` · `rejected`
  （中文名由 `services/progress.py` 提供，接口通过 `/api/status` 的 `progress_states` 给前端）
- 读接口会 JOIN `jobs` 带出 `title` / `company`（界面那两列要用）

### page_access（页面预算，防封号的核心）

```sql
id / platform / stage / day / created_at
```

- `stage`：`collect_search` · `collect_detail` · `apply` · `monitor`（外加 `total` 总量兜底）
- `day` 是**本地日期**；滚动窗口查询直接用 `created_at`
- 索引：`(platform, stage, day)`。速率窗口按 `(platform, created_at)` 查 —— 没有为它单独建索引，因为一天几百行，用 `platform` 前缀就够了

### locks（按平台冷却锁）

```sql
platform / reason / kind / until
```

- 每平台一行；`kind`：`captcha` · `rate_limit` · `blocked` · `page_failures`
- 只锁该平台（BossHunter 单行锁会导致连坐，本项目按平台隔离）

### runtime_kv（短生命周期状态）

```sql
key / value / updated_at
```

现有键：

| 键 | 含义 |
|---|---|
| `cooldown:{platform}` | 采集→投递冷却到什么时候 |
| `collect:{platform}:{slot}:p{page}` | 该「城市/关键词」第 N 页上次采完的时间（按页记账） |
| `penalty:{platform}` | 命中风控后的降速期到什么时候 |
| `last_open:{platform}` | 上一次开页面的时刻（epoch 秒）。节流间隔和界面倒计时都读它：每个请求 / 任务都是新 Policy，放内存会丢 |
| `page_failures:{platform}` | 连续「页面读不到预期内容」的次数，采集成功一次清零；到阈值锁平台 |
| `risk_platforms:{date}` | 当天命中过风控的平台（跨平台联动熔断用） |

### score_traces（评分依据快照）

```sql
job_id / model / prompt / tokens_in / tokens_out / latency_ms / created_at
```

回答"这个分数是怎么来的"：模型、提示词版本、token、耗时。

### task_runs（任务历史）

```sql
id / mode / platform / status / progress / logs / result / error / created_at / finished_at
```

- 开始写一行，结束更新同一行；`result` 是 JSON（全流程是 `{platform, steps:{...}}`）
- 记录页读它；失败时 `logs` 里带最后 12 行 traceback；索引 `created_at`

### tasks（早期遗留表）

保留但当前流程不用（任务态在内存 + `task_runs`）。

## 3. 岗位状态枚举

```
new → filtered / pending_confirm → approved → applied
                                        ↘ rejected（预筛或人工拒绝）
applied → already（平台显示已投过）/ need_resume（需完善简历）/ failed
```

代码里 `Status` 的完整取值：`new` · `rejected` · `filtered` · `pending_confirm` · `approved` ·
`applied` · `already` · `need_resume` · `failed` · `replied` · `interview`

- `APPLIED_STATUSES = {applied, already, replied, interview}`：算"已投过"，用于**重复投递防护**
- 每日投递额度不看状态，看 `applied` **事件**数（手动回执写的是同一个事件，所以口径一致）

## 4. 去重规则

1. 同平台同 `id` → 跳过（`upsert_job` 返回 `inserted=False`）
2. 跨平台：`normalize(company)` 与 `normalize(title)` 都相同 → 判为同一岗位，只留一条，
   另一条记 `dup_of` 并写 `cross_platform_dup` 事件
3. `normalize`：去空白 + 去 `-—_·・,，.。()（）[]【】/|` 等符号 + 转小写

## 5. 数据都在哪儿（备份/迁移用）

| 路径 | 内容 |
|---|---|
| `data/jobpilot.db` | 全部结构化数据（上表） |
| `config.yaml` | 平台/风控/模型配置（**含 API Key，别提交**） |
| `data/resumes/*.md` | 定制简历产物 |
| `data/serve.log` | 看板服务的 stdout + stderr（服务进程自己写；每次启动先写一行 `==== 启动 时间 ====`）。启动失败时 `data/launch-failed.txt` 会附上这次启动之后的部分 |

`GET /api/backup` 把前三项打成一个 zip（数据库用 SQLite 在线备份 API 出快照，不是直接拷文件）。
